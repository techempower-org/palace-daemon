# 2026-11-17: re-mines wiped whole transcripts

**Status:** resolved. Contained 09:05 PST, restored and verified 11:29; a second wipe at 11:32 was restored and its cause fixed by 12:48. Owner: the palace lane.

## What happened

Between 02:15 and 09:04 PST, 266,178 drawer ids were deleted from the shared collection. Nearly all of them went in
bursts of one minute each, and each burst emptied one large live transcript (wing, drawers, time PST):

| time | wing | drawers |
|---|---|---|
| 06:01 | money | 57,980 |
| 06:42 | plan | 21,806 |
| 07:23 | jp | 63,177 |
| 08:13 | realmwatch | 22,210 |
| 08:16 | wifey | 9,987 |
| 08:24 | infra (a host-ops wing) | 17,146 |
| 08:53 | palace | 641 |
| 08:55 | wifey (again, after the restore had begun) | 9,926 |
| 09:02 | jp (again) | 61,150 |

The night's dump (02:15) held 1,485,210 drawers; at 08:38 the live palace held 1,299,329. Three of the emptied
transcripts (200–330 MB each) were checked at 08:37: they held 0 or 1 drawers.

## Cause

1. The palace was slow. An autovacuum of `mempalace_drawers` had been in its index phase for over two hours, and the
   statement timeout is 30 s.
2. A growing transcript is re-mined incrementally. Under that load the miner's stored-drawer prefetch, or the
   metadata refresh of the unchanged drawers, failed. The fallback for either one treated every chunk of the file as
   changed: the prefetch fallback purged every drawer of the file, and the refresh fallback re-filed them all. The
   journal does not say which one fired for each file; both end the same way.
3. The re-file's 1000-row INSERT then hit the statement timeout.
4. On a write error, the miner's cleanup deleted every "changed" id so the next mine would see an incomplete file.
   After step 2, "changed" was the whole transcript, so it deleted every drawer of the file. The mine exited 1.
5. The daemon queues mines, and its drain kept replaying them. Every large live transcript was exposed.

Containment had a gap of its own. The bench-active lock, set at 08:40, stops new `POST /mine` calls and the watcher,
but the drain of already-queued mines ignored it. 71,717 more drawers went after the lock. At 09:04 the daemon was
restarted with an unreachable `PALACE_MINE_MIN_FREE_GB`, which the drain does honour (it requeues every entry). The
delete queue then showed no new deletes.

## Fixes

- **mempalace (miner):**
  - A failed prefetch aborts the file and deletes nothing.
  - A failed write deletes only rows the pass created, never a drawer that existed before it.
  - Stale drawers are deleted only after the pass has written its rows.
  - A batch skipped as "already exists" makes the pass incomplete: no orphan delete, no manifest.
  - The shared copies of chunks filed privately leave the shared collection at once, looked up by id.
  - INSERTs go in statements of at most 100 rows, each with its own KG write-through call.
- **palace-daemon (this repo):** the drain holds the queue while the bench lock or `PALACE_DISABLE_AUTOMINE` is on,
  the same requeue path as the disk floor.

## Restore

- **Source:** the 02:15 dump. Only ids that were in the KG delete queue and still absent were restored (190,865 rows;
  2,020 of the absent ids were filed after the dump and are not in it).
- **Method:** insert-if-absent (`ON CONFLICT DO NOTHING`), so no live row was updated.
- **Screening:** the dump predates that morning's private-key redaction, so every row was screened with the pem/ppk
  rules and against the scrubbed ids first. None matched.
- **Run:** in batches, in a session with its own 120 s statement timeout. To finish within hours, the autovacuum on
  `mempalace_drawers` was paused during the restore and is followed by a manual `VACUUM (ANALYZE)`.
- **Result:** 190,865 rows, then a second pass over ids still absent: 124 more (2,884 of those were filed after the dump,
  so it does not hold them; their transcripts re-file them on the next mine).
- **Verified 11:29, in a fresh session:** 0 of the 190,865 restored ids absent; 1,490,783 live drawers against the
  dump's 1,485,210; each of six emptied transcripts searchable, a query built from one of its own drawers returning
  that transcript in 4 to 10 of the top 10.

## The second wipe (11:32)

The pause came off at 11:29. The drain's first mine was the infra transcript, and it deleted all of that transcript's
drawers again: 17,574 ids (16,956 that existed before the pass, 618 the pass had just written).

1. Those drawers had been stored with a `source_file` whose project directory segment the broad token redaction had
   replaced with a placeholder (see below). The miner's prefetch looked them up by the real path and found none.
2. The pass's write met the same ids under a different `source_file`, and the pre-write collision scan stopped it.
3. The first fix's cleanup deleted "every changed id not in the prefetch". With an empty prefetch, that was every id.

The pause went back on at 11:34, and the fixes below were deployed before it came off again:

- **mempalace (miner):** before any write, a pass asks the collection which of its ids exist, by id, never by
  `source_file`. The cleanup after a failed write spares every id that existed; a failed lookup stops the file.
- **mempalace (redaction):** `source_file`, `source_path`, `drawer_id`, `id` and `ids` holding one value skip only the
  broad shapes. Provider keys, configured patterns, vault values, codes and named assignments still apply there.
- **Restore:** the 16,956 ids from a dump taken at 11:29, insert-if-absent; the infra transcript back to 16,957 drawers, searchable.
- **Path repair:** 17,930 rows (17,483 shared, 447 private) had a placeholder in `source_file`. Each real path was
  derived, never guessed: a file on disk was accepted only when redacting its path reproduced the stored string exactly,
  and exactly one file did, for all 164 distinct paths. Rows were backed up (0600) and updated by compare-and-set; a
  fresh session showed 0 placeholders left and every repaired path present on disk.
- **Proof before the drain:** the infra transcript was re-mined alone on the fixed code with a live count guard. Its
  count went 16,957 to 17,631 and never below 16,957; 0 deletes. Mining resumed at 12:47.

Afterwards a failed write in one transcript (a statement timeout) removed 383 rows, all written by that same pass and
none present in the 11:29 dump: the fixed cleanup working as intended.

## Found on the way

A path segment in some drawers' `source_file` metadata had been replaced by a `[redacted token …]` placeholder: the
broad token shape matched a project directory name. That caused the second wipe; it is fixed and repaired above.
